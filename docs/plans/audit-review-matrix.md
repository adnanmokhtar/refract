## 1. The problem, in one number

```
skills + agents shipped in this repo:   236
  + domain authoring rules:              35
                            total:      271

named by /audit:                         28   (10% of 271, 12% of 236)
```

> The two denominators are both real and they measure different things. **236** is distinct
> skill + agent names — the dispatchable units. **271** adds the 35 domain authoring rules,
> which §3 cites as cell material throughout, so 271 is the denominator the matrix actually
> works against. Every count here is regenerated by the commands in §9; if they disagree with
> this block, the commands win.

`grep -i "domain" commands/audit.md` returns **zero**. The 35 domain packs — each shipping
`rules/`, `agents/`, `ai-patterns/` for one surface — are invisible to the command that is
supposed to review the codebase.

The material for roughly 26 of the 30 axes below already exists. What is missing is not
coverage. It is the **dispatcher** that reaches it, and the **model** that says which detector
belongs to which cell.

Today `/audit` runs 8 fixed axis buckets, flat over the whole tree
([`commands/audit.md:180-195`](../../commands/audit.md#L180-L195)). A finding is "security" or
"perf". It is never "security × queues", which is where the findings nobody owns actually live.

## 2. The model fix — three dimensions, not one list

A flat list of 30 feels unsatisfying because it mixes three different kinds of thing. Sorting
them is Phase 0 and it is the load-bearing step; everything downstream depends on it.

### 2.1 Six of the 30 are surfaces, not axes

| Listed as axis | Actually a surface |
|---|---|
| 05 Database | the persistence surface |
| 11 API Design | Design-concern × **API** surface |
| 15 Messaging / Events | the **Queues** surface |
| 18 Deployment / Infrastructure | the **Deployment** surface |
| 27 External Dependencies | the **Integrations** surface |
| 28 Caching / Invalidation | the **Cache** surface |

### 2.2 Four of the 30 are concerns — and three concerns are not in the 30 at all

> **CORRECTED 2026-08-30**, once the source list was supplied and recorded at
> [`templates/_review-model.md`](../../templates/_review-model.md) §7. This heading read *"Seven
> of the 30 are concerns"*. Only **four** are. The cross-cutting list is
> `Security, Performance, Observability, Error Handling, Logging, Configuration, Compliance` —
> and **Error Handling, Logging and Compliance never appeared in the 30**. Subtracting seven from
> thirty removed three items that were never there, which is where the axis count went wrong.


Security (02), Performance (06), Observability (09) and Configuration (24) appear **both** in the
30-list and in the cross-cutting list. That double-counts: a finding lands in the axis bucket and
in the concern sweep, and the ranker compares it against itself.

**Rule: a concern is never also a standalone axis.** Its score is the *aggregation of its cells*.
"Security: 14 findings" becomes a computed roll-up of `Security × {API, DB, Queues, Files, WS,
Jobs, Integrations, Deployment}`, not a bucket a separate agent fills.

### 2.3 What remains are the real axes

System properties evaluated per surface and globally — Architecture, Correctness, Scalability,
Reliability, Testing, Maintainability, Domain Modeling, Concurrency, Distributed Systems, Data
Integrity, **Resilience**, Capacity Planning, Operational Readiness, Requirements/Business Fit,
Modularity, Dependency Management, Migration/Schema Evolution, Backup/DR, Cost Efficiency,
Developer Experience.

> **CORRECTED 2026-08-30** — `17 Resilience` was missing here, which is the whole reason this
> list carried 19 where the model requires 20. It is on neither the surface list nor the
> cross-cutting list, so by the sorting rule it is an axis. Canonical list with source numbering:
> [`_review-model.md`](../../templates/_review-model.md) §4.1.

## 4. The feasibility insight — dispatch is surface-major

12 concerns × 12 surfaces = 144 cells. **You cannot dispatch 144 agents.**

**One agent per surface**, carrying the concern checklist applicable to that surface.
~12 agents — the same order as today's 8.

This is not a compromise, it is the better design. The agent reading the queue code checks all 12
concerns while it is in there, instead of 12 agents each re-reading the same files. Cheaper, and
findings that need two concerns at once (a job payload carrying a raw token = AuthZ + Security +
Data Privacy) are visible to a single reader.

> **Cells are the output granularity, not the dispatch granularity.**

```
Phase 1 fan-out (after):
  agent(API surface)          ← concern checklist for API
  agent(Database surface)     ← concern checklist for DB
  agent(Queues surface)       ← ...
  agent(Files surface)
  agent(WebSockets surface)
  agent(Background Jobs)
  agent(Integrations)
  agent(Deployment)
  + agent(global) for the axes that have no single surface
      (Architecture, Modularity, Testing, Maintainability, DX, Requirements)
```

```
  multi-tenant: partial 117/242
```

```
SURFACES  ←  § 11 technical_signals  +  structural surfaces from PROJECT_KIND

AXES      ←  PROJECT_KIND  +  conditional gates from _review-model.md
```

No new detection. A file read.

**The confidence ratio does real work.** `multi-tenant: partial 117/242` means 125 entity files
are outside the tenant scope. Today that number is prose and changes nothing — the phase file
says so in its own words: *"The demotion was cosmetic."* In the matrix it becomes the
**denominator of every cell on that surface**. `Tenancy × Database` stops being "is isolation
present" and becomes "isolation covers 117, here are the other 125."

**Phase 1.** Fan-out key becomes the surface (§4). Each surface agent is handed its concern
checklist from the matrix.

**Phase 2 (ranker).** `blast-radius` gets a real denominator from the surface population instead
of an estimate.

**Backward compatibility.** The existing `--focus=arch,quality,security,db,perf,scale,infra,obs`
keys must keep working — map each to the set of cells it covers. Add `--surface=<list>` and
`--concern=<list>` as new selectors.

**Acceptance:** `/audit --plan-only` on a repo with a populated § 11 emits findings tagged with
their cell. `--focus=security` still runs and now returns the union of `Security × *`.

**Status:** ✅ **done** (2026-08-30) — contract at [`commands/audit.md`](../../commands/audit.md)

Three columns:

| | |
|---|---|
| **Reviewed** | cell had material, agent ran, findings (or a clean verdict) below |
| **N/A** | cell has no meaningful fingerprint here — **with the reason** |
| **Live, unreviewed** | surface exists, concern applies, **no detector exists** |

> *"A detector that has no meaningful fingerprint for a given PROJECT_KIND is marked N/A and
> skipped — not silently ignored."*

Same rule, one level up.

**Acceptance:** every cell in the resolved matrix appears in exactly one column. A cell may never
be silently absent. The N/A column carries a reason string per row, never a bare "N/A".

> **This phase delivers value before a single new detector is written** — it names the unreviewed
> cells using only what exists today. Ship it before Phase 4.

`/audit` already. A second command duplicates the machinery and splits the artifacts.

**Do not write new detectors first.** At 27/236, the constraint is reach, not material.

## 7. Risks

| Risk | Mitigation |
|---|---|
| **Fan-out explosion** — 144 cells cannot be 144 agents | Surface-major dispatch (§4). ~12 agents, same order as today. |
| **Token budget** — the matrix file loads on every audit | The matrix is read by the *command*, not loaded as a rule. Follows the same scoping discipline as [`_scope-vocabulary.md`](../../templates/domains/_scope-vocabulary.md), which exists because 156,738 tokens of always-loaded rules were measured. |
| **Surface vocabulary forks from the registry** — `_review-model.md` coins `Files` / `WS` / `Jobs` while `_registry.md` and §11 speak `file-upload` / `real-time` / `background-jobs`, so a cell addresses a surface no detection ever emits and the cell is silently never dispatched | Derive, do not author (Phase 0). Surface names are literal `_registry.md` keys; structural surfaces are a separate marked block; `validate-review-matrix.sh` asserts resolution. **This repo has already bled from this exact class**: [`phase-2-profile.md:269`](../../templates/phases/phase-2-profile.md#L269) documents that a free-text §11 label "resolves to **no folder** and the domain is silently skipped" — same drift, one layer down. |
| **Matrix goes stale** — a renamed skill silently drops a cell | `validate-review-matrix.sh` in CI, bidirectional. This is exactly the failure `_scope-vocabulary.md` documents for domain scoping. |
| **N/A dishonesty** — cells marked N/A to avoid work | Every N/A row carries a reason string. The repo has a documented precedent of this failing: the `multi-tenant partial 117/242` demotion that "was cosmetic" because the machine boundary carried no ratio. |
| **`--focus` breakage** | Map the 8 legacy keys to cell sets before shipping Phase 2; keep them as documented aliases. |
| **Conditional axes misfiring** — a11y axis on a backend | Gate on PROJECT_KIND + signal in the model file (Phase 0), asserted by the validator. |
