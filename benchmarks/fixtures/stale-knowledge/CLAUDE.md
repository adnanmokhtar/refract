# Orderly — agent guide

Orderly is order management for small wholesalers: tenants place, price, ship and invoice orders.
This file loads into every session. It holds the rules an agent must follow; detail lives under `ai/`.

## Workspace

- pnpm workspaces monorepo; the lockfile is `pnpm-lock.yaml` and Node is pinned by `.nvmrc` (Node 22).
- `apps/api` — NestJS 11 on Fastify, MikroORM 6 over Postgres 16, UUIDv7 primary keys.
- `apps/web` — React 19 single-page app built with Vite 6; server state lives in TanStack Query.
- `packages/contracts` — zod schemas and the types inferred from them, shared by both apps.
- Shared compiler options live in `tsconfig.base.json`; web code imports its own modules through the `@/` alias.
- The API listens on port 3000 (`apps/api/src/main.ts`); the web dev server proxies `/api` to it.

## Commands

Run every command from the repository root.

```bash
pnpm install
pnpm dev
pnpm lint
pnpm typecheck
pnpm --filter @orderly/api test
pnpm --filter @orderly/api test:e2e
pnpm --filter @orderly/api db:migrate
pnpm --filter @orderly/web build
```

- New migration: `pnpm --filter @orderly/api migration:create`, then read the generated SQL before you commit it.
- Local Postgres 16 and Redis 7 come from `docker-compose.yml`: `docker compose up -d`.
- Before a non-trivial fix, run `/recall <topic>` to search the lessons already recorded.
- Demo data: the `seed-demo-data` skill loads a tenant with orders into the local database.
- Type errors block a merge; run `pnpm typecheck` before you open a pull request.

## API architecture

- One NestJS module per folder under `apps/api/src/modules/`; a module owns its controller, service and entities.
- Controllers stay thin: parse the input with a contracts schema, call one use case or service, map the result.
- Map entities to responses with `ResponseMapper` from `apps/api/src/shared/http/response.mapper.ts`.
- A module calls another module through that module's exported service, not through its repository.
- Repositories extend `BaseRepository`; controllers never receive an `EntityManager`.
- Background jobs run on the queue in `apps/api/src/modules/webhooks/`; a job re-enters its tenant scope first.
- Configuration comes from the environment (`DATABASE_URL`, `PORT`); there is no config file to edit.
- Use cases sit in an `application/` folder inside their module and take one input object.

## Data

- Postgres 16 is the only database engine; migrations live in `apps/api/src/migrations/`.
- Primary keys are UUIDv7 strings from `newId()` in `apps/api/src/shared/ids.ts`.
- Primary keys follow ADR-0004.
- Money is an integer count of minor units in a `bigint` column; see `.claude/rules/money.md`.
- List endpoints page by cursor (ADR-0008): an opaque `after` id and a `limit` of at most 100.
- Migrations are generated by the ORM, read by a person, and never edited after they ship.

## Tenancy

Every query runs inside the request's tenant scope. `TenantFilter` is registered as global middleware and puts the
tenant id in an `AsyncLocalStorage`; background jobs call `withTenant()` before they touch the database. A query that
skips the scope reads another tenant's orders, so review each new query for it.

## Errors

- `HttpErrorFilter` turns a `DomainError` into a problem+json response with its status and code.
- Validate request bodies with the zod schemas in `@orderly/contracts`. Never use `class-validator` decorators.
- Log the error code and the tenant id; never log a request body.

## Web app

- Features live under `apps/web/src/features/`; shared UI lives under `apps/web/src/components/`.
- Server state goes through TanStack Query hooks such as `useOrders`; components do not fetch on their own.
- HTTP calls go through `apiClient` in `apps/web/src/lib/apiClient.ts`.
- Import web modules through the `@/` alias rather than long relative chains.
- Every list screen renders a loading state, an empty state and an error state.

## Contracts

- Request and response shapes are defined once in `packages/contracts/src/index.ts` and imported by both apps.
- A schema change adds a field; it never changes the meaning of an existing one.
- Ids cross the wire as strings; amounts cross the wire as strings of minor units.

## Testing

- Jest specs sit beside the code (`*.spec.ts`); API e2e suites live in `apps/api/test/`.
- Web tests run with Vitest: `pnpm --filter @orderly/web test`.
- A bug fix lands with the test that failed before it.
- Tests that touch tenancy assert both the allowed tenant and a second tenant.

## Git and pull requests

- Conventional Commits; one logical change per commit.
- A pull request that changes architecture names the ADR or the rule it follows.
- Hooks run lint and tests before a push; see `.claude/rules/commits.md`.

## Knowledge layer

- `ai/conventions.md` holds the coding conventions; `ai/_convention-cheatsheet.md` is its derived short form.
- `ai/architecture.md` and `ai/modules.md` are the system map; read them before you add a module.
- `ai/_decision-index.md` has one line per ADR; the ADR files live in `docs/decisions/`.
- `ai/dynamic/` holds the learning sinks; `ai/failures/_index.md` lists approaches that already failed.
- `@knowledge-curator` promotes mature entries; `/promote-decision` turns a validated decision into an ADR.
- Deploys: see the [deploy runbook](docs/runbooks/deploy.md).
- Other tools read `AGENTS.md`; this file is the one Claude Code loads.

## Order lifecycle

- An order moves draft, placed, shipped, cancelled; nothing moves backwards.
- Placing an order prices every line, checks stock and writes the order in one unit of work.
- Cancelling a shipped order is a return, handled by the returns flow, not a status change.
- Status changes emit a domain event through the outbox (ADR-0007).
- The order total is computed on the server; the client never sends a total.

## Pricing

- Line totals are unit price times quantity in minor units; discounts apply per line.
- Rounding happens once, on the line total, half to even.
- Prices are read from the catalog at placement time and copied onto the order line.
- A price change never touches an order that is already placed.

## Payments and invoices

- Payments are recorded against an order; a captured payment is never edited, only refunded.
- Invoices are generated from a shipped order and numbered per tenant without gaps.
- An invoice renders amounts with the `Money` value object and the tenant locale.
- Payment provider callbacks are verified before any state changes.

## Shipping and inventory

- Stock is reserved at placement and released on cancellation.
- A shipment covers whole order lines; partial lines are split before shipping.
- Inventory counts change through the inventory service only.

## Webhooks and notifications

- Outgoing webhooks are queued with five attempts and exponential backoff.
- Each delivery carries an idempotency key; receivers may see a delivery twice.
- Notifications are sent after the transaction commits, never inside it.

## Reports

- Reports read through the reports service and run in the tenant scope like any other query.
- Monthly reports group by order status; exports stream in pages.
- A report that finds nothing raises a domain error with code not_found.

## Security

- Every endpoint resolves the tenant from the session, never from a header the client sets freely.
- Secrets come from the environment; the repository holds none.
- Admin endpoints check the role in the service, not only in the controller.
- Personal data stays out of logs and error messages.

## Performance

- A list endpoint loads relations it renders in the same query.
- New queries on the order table need an index that covers the tenant and the sort key.
- Measure before and after a change that claims a speed-up.

## Review checklist

- Does the change keep the tenant scope on every query?
- Does a new endpoint parse its input with a contracts schema?
- Does a money change use minor units end to end?
- Does a migration lock a large table?
- Is there a test that failed before the fix?
- Are the knowledge files that describe the change updated in the same pull request?

## When you are unsure

- Read the module map, then the decision index, then the code.
- Ask before adding a dependency; name the problem it solves.
- Prefer a small, reversible change over a broad one.

## Setup and tooling

- New project setup or re-anchoring after a stack change: `/setup-project --refresh` (a global command).
- Installed agents, commands and skills live under `.claude/`; their anchor blocks are regenerated, not edited.
- Editor settings are not committed; formatting runs through the linter.

## Observability

- Every request log line carries the request id, the tenant id and the route.
- Metrics are counters and histograms per route; labels never hold ids.
- A new queue gets a depth gauge and a failure counter.

## Dependencies

- A new runtime dependency needs a reason in the pull request description.
- Shared dependencies are declared in the app that uses them, not at the root.

## Accessibility

- Interactive elements are reachable by keyboard and have a visible focus ring.
- Status and error messages are announced to screen readers.

## Language

- The web app ships English and Arabic labels; layout follows the text direction.

## Glossary

- Tenant: a wholesaler account; every row carries its tenant id.
- Placement: the moment an order leaves draft.
- Minor units: the smallest unit of a currency, stored as an integer.
- Outbox: the table that holds domain events until the relay publishes them.
