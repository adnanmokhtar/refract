# Cline / Roo adapter

**Tool:** Cline (VS Code extension) — Roo is a Cline fork with similar conventions.
**Docs:** https://docs.cline.bot/features/cline-rules · https://docs.cline.bot/customization/workflows · https://docs.cline.bot/features/hooks
**Capabilities:** R, **S (native skills — PRIMARY for action workflows; experimental, must enable in Settings → Features → Enable Skills; also reads `.claude/skills/` directly)**, C (legacy — `.clinerules/workflows/` slash commands, graded fallback), **H (native hooks — `.clinerules/hooks/<Event>` since v3.36; macOS/Linux only)**. No native agents.

> **Skills-first correction (2026-05-14, verified against docs.cline.bot)**: Cline has **merged workflows into Skills** — the separate workflows docs page now 404s; skills is the unified primitive. Cline auto-discovers skills from `.cline/skills/`, `.clinerules/skills/`, **AND `.claude/skills/`** (so Claude Code skills work in Cline without duplication). Action commands map **primarily to `.cline/skills/<name>/SKILL.md`** (or, for projects that also have Claude Code installed, the existing `.claude/skills/<name>/SKILL.md` works directly — no separate Cline file needed). Three-tier progressive loading (metadata ~100 tok → instructions <5K → resources) keeps context lean. Legacy `.clinerules/workflows/<name>.md` still works as a **graded fallback** — written alongside the skill so older `/<workflow-name>` muscle-memory keeps working; new projects generate skills first. This mirrors the cursor skills-first contract: the **primary** surface is graded, the workflow mirror is a deprecation-path fallback.

> **Cline standalone goal**: a project generated by `/setup-project` with the `cline` adapter selected MUST work end-to-end in Cline with **no `.claude/` present**. Rules attach automatically; skills surface via auto-discovery + `/<skill-name>` slash; agents fall back to documented sections in `.clinerules/` (Cline has no native agent primitive).

## Target files

```
repo-root/
├── .cline/
│   └── skills/                               # NATIVE (PRIMARY) — one folder per action command + skill
│       └── <name>/
│           └── SKILL.md                      # Surfaces as /<name> + auto-discovered by description
├── .clinerules/                              # Folder (preferred over legacy single file)
│   ├── 00-project.md                         # Always-loaded project rules
│   ├── 10-<domain>.md                        # Per-domain rules
│   ├── 20-<stack>.md                         # Per-stack rules
│   ├── 81-agents.md                          # Persona index (no native dispatch)
│   ├── 82-skills.md                          # Procedure index (catalog; PRIMARY surface is .cline/skills/)
│   └── workflows/                            # FALLBACK — legacy Cline slash commands (graded fallback)
│       └── <workflow-name>.md                # Becomes /<workflow-name> in Cline chat
└── AGENTS.md                                  # Cline also reads this as fallback
```

**Legacy single-file `.clinerules`:** older Cline versions read a single file. Treat as deprecated; folder-style is now documented default. If `.clinerules` file exists from a prior setup, leave it and write folder-style alongside (folder takes precedence).

## File formats

### `.clinerules/*.md`
Plain markdown. No frontmatter required — Cline loads every `.md` + `.txt` in the folder alphabetically. Ordering matters (use `00-`, `10-`, `20-` prefix for predictable precedence).

Cline is reported to read `.cursorrules`, `.windsurfrules`, and `AGENTS.md` from repo root as additional rule sources — verify against https://docs.cline.bot/features/cline-rules before relying on it. If true, avoid duplicating content across these files: Cline concatenates everything it finds, and duplicates waste context.

## Translation recipe

1. **`.clinerules/00-project.md`** — project-wide rules:
   - Read-before-edit principle
   - Architecture summary
   - Top 5-10 MUST / MUST NOT rules
2. **`.clinerules/<NN>-<domain>.md`** — one file per `.claude/rules/<domain>.md` (one-to-one, **REQUIRED by Phase 4.8.0 contract**, not optional). `<NN>` ∈ {10..79}:
   - Copy from `.claude/rules/<domain>.md` verbatim (Cline doesn't support includes).
   - Numeric prefix groups related rules (10-19 = always-relevant; 20-29 = stack-specific; 30-79 = domain/feature-specific).
3. **`.clinerules/20-<stack>.md`** — stack-specific (nestjs, vue, react):
   - Copy relevant pack rules.

Since Cline has no glob-based scoping, path-scoped rules must be written as prose ("When editing database code...").

## Idempotency

Each generated `.md` has a marker:
```markdown
<!-- GENERATED BY claude-setup-project. User edits below persist. -->
```
Generator overwrites everything above the marker.

User-owned convention: prefix custom files with `90-user-*.md`. Generator never touches those.

## Known gotchas

- Numeric prefix isn't enforced by Cline — it just loads alphabetically. Stick to two-digit prefixes for consistency.
- Cline reads ALL of: `.clinerules/*.md`, `.clinerules` (file), `.cursorrules`, `.windsurfrules`, `AGENTS.md`. Content duplicated across multiple sources is a context-waste risk.
- No character limit documented but keep total rule budget under ~15k tokens; Cline's performance degrades with long rule stacks.
- Cline supports `/newrule` slash command to create rules interactively. Leave `.clinerules/90-user-*.md` namespace free for that.

## Full artifact translation

### Commands — `.claude/commands/<name>.md` → `.cline/skills/<name>/SKILL.md` (PRIMARY) + `.clinerules/workflows/<name>.md` (graded fallback)

Per the **Skills-first correction** at the top of this adapter, action commands translate **primarily to a native Cline Skill** at `.cline/skills/<name>/SKILL.md` — Cline auto-discovers it (from `.cline/skills/`, `.clinerules/skills/`, AND `.claude/skills/`), surfaces it as `/<name>`, AND auto-matches it by description. A `.clinerules/workflows/<name>.md` mirror is ALSO written as a **graded fallback** (still works today; the workflows docs page now 404s) so existing `/<name>` muscle-memory keeps working until the user is fully on Skills.

**Primary** — `.cline/skills/<name>/SKILL.md` (needs a `name:` field the source command lacks, so this is LLM-authored, not a raw copy):

```markdown

<!-- GENERATED BY claude-setup-project. User edits below persist. -->
```

**Fallback** — `.clinerules/workflows/<name>.md` (1:1 mirror of the source, no frontmatter — Cline recognises the file directly):

### Hooks — `.claude/hooks/*.sh` → Cline native hooks (`.clinerules/hooks/`)

**Native support:** full `✓` (since **Cline v3.36**, 2025-11-06). Cline has a real lifecycle-hook system with blocking + context-injection — no longer a git-hook-only fallback.

**Native mechanism:** executable scripts in **`.clinerules/hooks/`** (project) or **`~/Documents/Cline/Rules/Hooks/`** (global). The **filename is the event name, no extension** (e.g. `.clinerules/hooks/PreToolUse`), and the file must be executable. Six events: **PreToolUse** (can block), **PostToolUse**, **UserPromptSubmit**, **TaskStart**, **TaskResume**, **TaskCancel**. Each hook receives context as JSON on **stdin** and returns JSON on stdout: `{"cancel": true, "errorMessage": "…"}` blocks the operation; `{"cancel": false, "contextModification": "…"}` injects text into the conversation to steer future decisions.

```
.clinerules/hooks/
├── PreToolUse          # guard/scan — return {"cancel":true,...} to block
├── PostToolUse         # lint / format / test after an edit
└── TaskStart           # session briefing via contextModification
```

**Translation of the repo's hooks:**
- `guard-destructive.sh` + `pre-edit-guard.sh` + `secret-scan.sh` → **`PreToolUse`** (native) — inspect `tool name + params` from stdin, emit `{"cancel":true,"errorMessage":"blocked .env write"}` to hard-block. Keep `.husky/pre-commit` as a defence-in-depth git hook.
- `post-edit-check.sh` + `format-on-save.sh` + `auto-test.sh` → **`PostToolUse`** (native) — receives tool result + timing; run lint/format/test.
- `session-start.sh` (SessionStart) → **`TaskStart`** (native) — inject "read `ai/status.md`" via `contextModification`.
- `inject-path-rules.sh` → best as **path-scoped `.clinerules`** (always-apply rules), or `PreToolUse` `contextModification` keyed on the edited path.
- `update-session-log.sh` (Stop) → nearest native is **`TaskCancel`** (cleanup on task end); no exact Stop event — otherwise keep the manual "append to `ai/dynamic/session-log.md`" rule.
- `notify.sh` → **n/a** (no notification event) — drop or route through `PostToolUse`.

**Caveats:** hooks run on **macOS and Linux only — no Windows support**; provide the `.husky/` git-hook fallback for Windows contributors. Repo scripts read Claude Code's hook payload schema; they must be adapted to Cline's stdin JSON (`cancel`/`errorMessage`/`contextModification` contract) — not drop-in. Disclose residual gaps in `.clinerules/00-project.md`.

**Source:** https://docs.cline.bot/features/hooks · https://cline.bot/blog/cline-v3-36-hooks
