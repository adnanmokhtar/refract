# Migration v1 → v2

The M2 split of `/setup-project`. v1 generated artifacts assumed a monolithic command; v2 expects pluggable phases, idempotency markers, and managed sections.

This migration is **idempotent** — running twice on the same repo is a no-op the second time.

## What changes in artifacts

| v1 artifact behavior                                          | v2 artifact behavior                                 |
|---------------------------------------------------------------|------------------------------------------------------|
| CLAUDE.md fully regenerated each run                          | CLAUDE.md regenerated only inside managed markers    |
| `ai/conventions.md` overwritten                               | Managed sections regenerated; user sections kept     |
| ADRs editable                                                 | ADRs append-only (already was; now enforced)         |
| `_session-digest.md` hand-written                             | Auto-regenerated by knowledge-curator                |
| Tool adapters scattered through `/setup-project`              | `/setup-project-adapters` sibling command            |
| Setup version untracked                                       | `setup-project: vN` stamped in every managed marker  |

## Detection (am I a v1 repo?)

A repo is v1 if ANY of:

- `CLAUDE.md` contains no `<!-- setup-project:managed start ... -->` markers AND was last touched by a setup run.
- `.claude/codebase-profile.md` lacks a `Setup version` section.
- `ai/_session-digest.md` is missing entirely.

## Migration steps

The runner (`scripts/migrate-setup.sh v1-to-v2 <target-repo>`) executes these in order. Each step is a separate function so a partial run can resume.

### Step 1 — Backup

Mirror the existing `.claude/`, `ai/`, `CLAUDE.md`, `AGENTS.md` into `.claude/backups/v1-pre-migration-<timestamp>/`. Hard rule N20 keeps the backup forever; the user removes it when comfortable.

### Step 2 — Wrap existing managed regions in markers

For each known v1 artifact (CLAUDE.md, ai/conventions.md, .claude/rules/*.md), parse it and identify the regenerable region by heading. Wrap with:

```
<!-- setup-project:managed start id=<artifact-id> v=2.0.0 -->
... existing content ...
<!-- setup-project:managed end -->
```

Heuristic for the regenerable region in CLAUDE.md: from the first heading that matches `^## (Project at a glance|Detected stack|Required reading|Decision boundaries)` through the last heading that matches `^## (Read-before-edit|Tiered context loading)`. Everything else is treated as user content.

User-authored detail (e.g., a project-specific section the user wrote between two managed sections) is preserved as a `setup-project:user` block — same syntax, different prefix.

### Step 3 — Stamp version

Write `Setup version: 2.0.0` and the run timestamp into `.claude/codebase-profile.md` under a `## Setup version` section (creating the file if missing).

### Step 4 — Bootstrap derived files

Create `ai/_session-digest.md`, `ai/_convention-cheatsheet.md`, `ai/_decision-index.md` by running the curator agent in regen mode against current `ai/` content. These are derived projections — never hand-edited.

### Step 5 — Move adapter detail (no-op for repos without adapters)

If `.cursor/`, `.opencode/`, `.aider*`, etc. exist, run `/setup-project-adapters` to re-translate from v2-shaped source artifacts. v1 adapters may have inlined rules; v2 adapters reference `.claude/rules/*.md` canonical files.

### Step 6 — Verify

Run `/setup-project-health` against the repo. Expected: at minimum `ok` on idempotency-markers + version-drift checks. Other checks may surface drift that pre-dates the migration — surface to user, do NOT auto-fix.

## What this migration does NOT do

- **Does not regenerate ADRs.** They are preserved verbatim (rule N19).
- **Does not delete the v1 backup.** The user owns deletion.
- **Does not touch user-authored sections.** Even within v1 files that lacked markers, the heuristic tries to identify and preserve them.
- **Does not change `.claude/settings.json` or `settings.local.json`.**

## Rollback

If migration ends unhappy:

```bash
rm -rf .claude/{settings.local.json-untouched,plus-everything-else}    # not actually destructive — see below
cp -R .claude/backups/v1-pre-migration-<timestamp>/* .
```

The runner emits the exact rollback command at the end of every run, parameterized to the actual backup path.

## When NOT to run this migration

- The repo was created post-v2.0.0 (`Setup version: 2.x` already stamped).
- The repo is a fresh `/setup-project` target with no prior setup output.
- The user explicitly chose `--no-upgrade` or is running v1.x of the command intentionally.
