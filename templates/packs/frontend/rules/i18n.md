# i18n Rules

> **Hard rule.** Translation field types MUST be dynamic-key (`Record<string, string>` or framework equivalent) — fixed-key shapes like `{ en: string; ar: string }` are forbidden. Every user-facing string MUST resolve through `t(...)` / `$t(...)` and exist in EVERY declared locale; active-language refs MUST read `locale.value` directly (no `=== 'en' ? 'en' : 'ar'` ternaries).

Stack-agnostic. Framework specifics in `references/<framework>.md` (vue, react, etc.).

Prevents the failures that ship: hardcoded 2-language assumptions, missing keys per locale, RTL bugs, copy-paste of legacy `{ en, ar }` literals into new code.

## Must

- Translation field type is **dynamic-key**: `Record<string, string>` (or framework-typed equivalent). Never `{ en: string; ar: string }` or any fixed-key shape.
- Initialise empty-translation values from the runtime-configured language list, NOT from a hardcoded literal. Use the project's empty-translations factory (e.g., `buildEmptyTranslations()`) rather than `{ en: '', ar: '' }`.
- Active-language refs hold a generic locale string (`ref(locale.value)`). Never `locale.value === 'en' ? 'en' : 'ar'` — that ternary reduces N languages to 2.
- Every user-facing string has an i18n key. Every key exists in EVERY declared locale file (translators write once; the audit catches drift).
- New keys live in the right scope: per-module locale files for module-scoped keys, shared locale files for cross-module keys (e.g., common buttons, route titles).
- RTL-aware CSS: use logical properties (`margin-inline-start`, `inset-inline-end`) — not physical (`margin-left`, `right`) — anywhere a direction-flipping language is supported.
- Runtime / user-supplied text of unknown direction carries its **own** direction: `dir="auto"` on the element holding it (the browser infers the base direction from the first strongly-typed character), `<bdi>` around inline insertions so surrounding text is not re-ordered, and `dirname` on the form field so the detected direction reaches the server for re-display. The root `dir` sets the *base* direction of the page; it cannot fix a single Arabic comment inside an English thread. ([W3C i18n — structural markup and RTL text](https://www.w3.org/International/questions/qa-html-dir))

## Must not

- `ref<Translations>({ en: '', ar: '' })` — hardcoded 2-language literal. Tenants/users with Spanish/French enabled get no input field; tenants who disable English/Arabic get stale dead keys.
- `locale.value === 'en' ? 'en' : 'ar'` — language enum that ignores N>2.
- Hardcoded user-facing strings: `<button>Save</button>` (use `t('common.save')`).
- Adding a key to only one locale file. Both/all locales must have it (CI catches this if a key-coverage check is wired).
- Copy-pasted V1/legacy translation literals into new code. Tooling helpers exist for a reason.
- Direction-flipping CSS that hardcodes `left`/`right`/`margin-left` instead of logical properties (breaks RTL silently).
- `dir="rtl"` hardcoded on individual elements as a **layout workaround** — the base direction belongs at the root, synced to the active locale. This bans the hack, not per-element `dir` as such: on runtime text of unknown direction it is required (see the `dir="auto"` Must above). Per W3C, use `dir` on a block element only when you need to *change* the base direction of the content in that block.

## Should

- Initialise translation refs in forms as `{}` (lazy fill) for forms where the user types only some languages, OR `buildEmptyTranslations()` (eager fill) for forms where every language's key MUST be present at submit time. Both are acceptable; pick one explicitly per form and document the choice.
- Watch the active locale for changes that affect data-fetch (e.g., when the API returns localised content) — refetch on locale switch and preserve filter/state across the watch.
- Run a single i18n-audit step in CI / pre-commit that catches missing keys per locale, hardcoded strings, locale-file drift, and unused keys.

## Review checklist

- [ ] No `{ en: '', ar: '' }` (or any fixed-key) translation literal in this diff.
- [ ] No `locale.value === '<en>' ? '<en>' : '<ar>'` ternary.
- [ ] Every new user-facing string has a key.
- [ ] Every new key exists in all declared locale files.
- [ ] Active-language ref reads `locale.value` directly.
- [ ] Direction-aware styling uses logical CSS properties.
- [ ] Any field or element rendering user-supplied text sets `dir="auto"` (+ `<bdi>` inline, `dirname` on the input).

## Enforcement

- Custom ESLint rule (or grep in pre-commit) for `{ en: ['"], ar: ['"] }` literal pattern.
- i18n-audit skill / `i18next-parser` / `vue-i18n-extract` / `nuxt/i18n` extractor — runs in CI; fails on missing keys per locale.
- Visual regression / Lighthouse on RTL routes — catches direction-flip bugs.

## Anti-patterns (named)

- **The Two-Locale Trap** — code assumes the platform supports exactly the two locales the developer happened to test with. Breaks the moment the product team enables a third. Always read available languages from runtime config.
- **The Ternary Reducer** — `locale === 'en' ? 'en' : 'ar'`. Reduces an N-language platform to 2. The intent is "default Arabic when locale isn't English" — but the implementation is "exactly two locales forever".
- **The Lazy Locale Fork** — adding a new key to `en.ts` and forgetting `ar.ts` (and vice versa). Catches the user as a missing-key warning at runtime. CI should fail this PR.
- **The Stale Empty-Translations Constant** — exporting `const EMPTY_TRANSLATIONS = { en: '', ar: '' }` as a "shared utility". Every consumer is now hardcoded. Replace with a factory function that reads runtime languages.
