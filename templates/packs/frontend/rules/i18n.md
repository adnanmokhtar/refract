# i18n Rules

> **Hard rule.** Translation field types MUST be dynamic-key (`Record<string, string>` or framework equivalent) — fixed-key shapes like `{ en: string; ar: string }` are forbidden. Every user-facing string MUST resolve through `t(...)` / `$t(...)` and exist in EVERY declared locale; active-language refs MUST read `locale.value` directly (no `=== 'en' ? 'en' : 'ar'` ternaries).

Stack-agnostic; framework specifics in `references/<framework>.md`. **This file owns one thing: the number of locales the code assumes.** Key coverage, unused keys, plural concat and cross-frontend drift are measured by `@i18n-auditor` and never restated here. What is left is the bug with no missing key and no failing test — code that is correct for the two locales the developer enabled, and structurally unable to hold a third.

## Must

- Translation field type is **dynamic-key**: `Record<string, string>` or the framework-typed equivalent. Never a fixed-key shape.
- Initialise empty-translation values from the runtime-configured language list via the project's factory — never from a literal.
- Active-language refs hold a generic locale string (`ref(locale.value)`). A two-branch ternary is not a narrowing, it is a cap on how many languages the product can ever ship.
- **Empty-translation init is decided by the submit contract, not by taste.** If the write endpoint rejects a translation map missing a declared locale, eager-fill from the factory so the shape is always complete. If it accepts and merges a partial map, initialise `{}` — an eager fill there writes empty strings over existing translations on every edit, and nothing catches it, because the payload is well-formed and the request succeeds. Read the endpoint once and record the answer in the anchored block above.
- New keys live in the right scope: per-module files for module-scoped keys, shared files for cross-module keys (common buttons, route titles). The same key duplicated into three modules is three strings a translator must keep in sync.
- RTL-aware CSS: logical properties (`margin-inline-start`, `inset-inline-end`), not physical (`margin-left`, `right`), anywhere a direction-flipping language is supported.
- Runtime / user-supplied text of unknown direction carries its **own** direction: `dir="auto"` on the element holding it (the browser infers base direction from the first strongly-typed character), `<bdi>` around inline insertions so surrounding text is not re-ordered, and `dirname` on the form field so the detected direction reaches the server for re-display. The root `dir` sets the *base* direction of the page; it cannot fix a single Arabic comment inside an English thread. ([W3C i18n — structural markup and RTL text](https://www.w3.org/International/questions/qa-html-dir))

## Must not

- `ref<Translations>({ en: '', ar: '' })` — a hardcoded 2-language literal. Tenants with a third language enabled get no input field for it; tenants who disable one get stale dead keys nothing can reach to remove.
- `locale.value === 'en' ? 'en' : 'ar'` — a language enum that ignores N > 2.
- `dir="rtl"` hardcoded on an individual element as a **layout workaround** — base direction belongs at the root, synced to the active locale. This bans the hack, not per-element `dir` as such: on runtime text of unknown direction it is required (see the `dir="auto"` Must above). Per W3C, set `dir` on a block element only when you need to *change* the base direction of that block's content.

## Anti-patterns (named)

Naming them is what makes them refusable in review; "this looks like a two-locale assumption" loses an argument that "this is The Two-Locale Trap" wins.

- **The Two-Locale Trap** — code assumes the platform supports exactly the two locales the developer tested with. Breaks the moment the product team enables a third. Read available languages from runtime config.
- **The Ternary Reducer** — `locale === 'en' ? 'en' : 'ar'`. The intent is "default to Arabic when the locale isn't English"; the implementation is "exactly two locales forever".
- **The Lazy Locale Fork** — a new key added to one locale file and forgotten in the others. Surfaces to the user as a missing-key warning at runtime. CI should fail this PR; `@i18n-auditor` files it as a BLOCKER.
- **The Stale Empty-Translations Constant** — exporting `const EMPTY_TRANSLATIONS = { en: '', ar: '' }` as a "shared utility". Every consumer is now hardcoded, and the constant is what makes the trap survive a refactor. Replace with a factory that reads runtime languages.
