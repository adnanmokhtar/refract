# Pattern: i18n

> **Hard rule:** A key names a **concept**, not a string of copy, and every plural passes through ICU rather than a ternary. Concatenating translated fragments to build a sentence, and formatting a date / number / currency without an explicit locale, are forbidden. Every finding cites the key or the call site at `<path:line>`.

**Scope — read this before adding anything here.** `.claude/rules/i18n.md` owns **how many locales the code assumes**: dynamic-key translation types, the ternary-reducer ban, the empty-translations factory, RTL logical properties and `dir="auto"`. `@i18n-auditor` owns **detection** — parity, unused and undefined keys, hardcoded strings. `/i18n-audit` owns the **extractor pass**. This pattern owns the four things none of them carry: **key architecture, ICU plurals, `Intl` formatting, and namespace loading.** A section added here that restates the rule or the auditor is a defect in this file.

**When to apply**
- The product ships in two or more languages, or will within 12 months.
- A key namespace is being designed, renamed, or split — that is a contract change, and this is the file that says why.
- Counts, dates, money or lists are being rendered into translated copy.

**When NOT to apply**
- Internal-only, single-language tooling with no localization plan — document the decision and gate strings later. Over-i18n-ing an admin tool read by five people who share a language has no payback.
- A throwaway prototype whose lifespan is shorter than the extraction cost.
- **A hosted translation platform that owns key naming and plural authoring end to end** (Phrase, Lokalise, Crowdin with enforced conventions) — mirror its conventions and cite them; do not impose a second key architecture beside one a translation team already works in.

**Halt conditions / mandatory cites**
- A new key MUST cite the namespace file it lands in at `<path:line>`; a key with no home is a key nobody can find to translate.
- Any plural MUST cite the ICU message, not the call site — the call site tells you nothing about which categories exist.
- Date / number / currency formatting MUST cite the locale-aware formatter, never a raw `toString` / template literal.
- If the project's i18n library and locale layout are not extracted, halt before adding strings.
- Hand-wave grep on `etc.`, `...`, `appears to`, `roughly` is forbidden when claiming strings are extracted.

## Key architecture

**Namespace by feature, not by page.** A `products` namespace is reused across list / detail / edit; a `page-1` namespace is unmaintainable the moment a page is renamed. The dot-path (`products.form.price_label`) is the ONLY identifier components reference: reorganizing files inside the locale directory is safe, **renaming a key is a contract change** — it breaks every other frontend and every in-flight translation job pointing at it.

**Name the key for the concept, never for the copy.** This is the rule that gets broken quietly, and it is not a style preference:

```
BAD:   products.form.create_product_button       // named after what it says today
GOOD:  products.form.submit_create               // named after what it does
```

When marketing changes "Create product" to "Add item", the BAD key still says `create_product_button` in every locale file, in the translation platform's UI, and in the code. Translators now read a key that contradicts its own value, and the next developer renames it — a contract change caused by a copy edit. A concept-named key survives every copy revision without a migration.

**Scope follows reuse, not convenience.** Module-scoped keys live in the module's locale files; genuinely cross-module strings (common buttons, route titles) live in the shared file. A module key duplicated into three modules is three strings a translator must keep in sync and three places a copy edit can miss.

## Plurals — ICU, and the two categories people get wrong

```ts
// WRONG — breaks in any language with non-trivial plural rules
const text = `${count} ${count === 1 ? 'order' : 'orders'}`;

// RIGHT — the ICU message in the locale file; the locale applies its own rules
// en.json: "{count, plural, =0 {No orders} one {# order} other {# orders}}"
// ar.json: "{count, plural, =0 {لا توجد طلبات} one {طلب واحد} two {طلبان} few {# طلبات} many {# طلبًا} other {# طلب}}"
const text = t('orders.count', { count: 5 });
```

Arabic distinguishes one, two, few (3-10), many (11-99) and other. Russian has separate forms for 1, 2-4 and 5+. English has one and other. ICU handles all of them; a ternary handles exactly one language and silently mistranslates the rest.

**The gotcha that ships broken keys: `=0` and `zero` are not the same thing.** `=0` is an exact-value match and works in every locale. `zero` is a CLDR *plural category*, and a language only ever selects it if its own plural rules define it — English does not. A `zero {No orders}` branch in `en.json` is dead: the runtime evaluates English's rules, gets `other`, and renders "0 orders". Use `=0` for the empty-state copy, and reserve `zero` for the locales whose rules actually select it.

**Never assemble a sentence from parts.** `t('order') + ' x ' + count` produces "Order x 5" in English and word-order gibberish elsewhere; `"Welcome, " + name + ", to " + product` breaks in Japanese and reverses in Arabic. One key, one whole sentence, interpolation inside the message — word order is the translator's to decide, and it is only theirs if the whole sentence is in the message.

## `Intl` — locale and currency are independent axes

```ts
// WRONG — locks to one locale's conventions, and to the runtime's
const formatted = `$${price.toFixed(2)}`;
const date = new Date().toLocaleDateString();

// RIGHT — explicit locale; currency is a separate argument, not a consequence of it
new Intl.NumberFormat(locale, { style: 'currency', currency }).format(4250);
//   en-US + USD → "$4,250.00"   ar-EG + USD → "٤٬٢٥٠٫٠٠ US$"   de-DE + EUR → "4.250,00 €"
```

**Currency is a property of the transaction, not of the reader.** A US user buying from a German store sees German prices in EUR: `locale` decides digits, grouping and symbol placement; `currency` decides which money it is. Deriving one from the other is how a price gets re-denominated by a formatter.

**Always pass an explicit `timeZone` to `Intl.DateTimeFormat`.** Omitted, it uses the *runtime's* zone — the container's (usually UTC) on the server, the user's in the browser. On a server-rendered route those are two different strings for the same instant, which is a hydration mismatch; `ssr-safety.md` detector 5 owns finding it, this pattern owns the reason it happens.

Prefer the i18n library's own wrappers (`n()`, `d()`, `$n`, `$d`) over raw `Intl` where they exist, so the active locale is bound once instead of threaded through every call site.

## Namespace loading

Do not ship every locale to every user — load the active locale, and split per namespace so a user on `/products` never downloads the `/admin/users` messages. Every major library (vue-i18n, react-i18next, next-intl) supports both.

**The cost, which is the part usually missed:** a namespace that has not arrived yet renders the raw key (`products.list.title`) or silently falls back to the pivot locale for one frame. Await the namespace's load in the same boundary that awaits the route's data, so the subtree never renders against messages it does not have. A locale switch has the same shape — the new bundle is a fetch, and the UI must not paint between the switch and its arrival.

## Cross-frontend key consistency

If several frontends share one workspace (admin + storefront + mobile), the same concept uses the **same key** in all of them. Translators write "Order total" once and every app inherits it. Diverging keys (`orders.list.total` in admin, `cart.summary.total` in storefront) double the translation cost, and they drift: the two get edited separately and the product now says two different things for one number.

## Detectors (cite-or-halt)

1. **Ternary plural.** BAD: `count === 1 ? 'order' : 'orders'`, or `${count} item${count > 1 ? 's' : ''}`. GOOD: an ICU `plural` message. Grep: `rg -n "\\? *['\"][^'\"]*['\"] *: *['\"]" src` near a count, and `rg -n "\\}s['\"]|s['\"] *: *['\"]"` for the suffix form. `report-with-fix`.
2. **Dead `zero` category.** A `zero {` branch in a locale whose CLDR rules never select it (English and most European locales). Grep: `rg -n '\bzero \{' locales/` then check the locale against its plural rules; if it cannot select `zero`, the branch is unreachable and the empty state is unhandled. `report-with-fix` — replace with `=0`.
3. **Concatenated translation.** BAD: `t('a') + ' ' + t('b')`, or a translated fragment joined to a variable. Grep: `rg -n "t\\([^)]*\\) *\\+|\\+ *t\\("`. `report-with-fix` — one key, one sentence, interpolation inside.
4. **Copy-named key.** A key whose leaf repeats its own English value (`create_product_button` → "Create product"). Grep: compare each pivot leaf segment against its value, tokenized; a high overlap is the smell. `[self-policed]` — the match is a judgement call, and a false rename is worse than the original key, so this one reports for a human and never auto-fixes.
5. **Formatting with no explicit locale.** BAD: `toLocaleDateString()` / `toLocaleString()` / `Intl.NumberFormat()` with an empty argument list. Grep: `rg -n 'toLocale(Date|Time)?String\\(\\)|Intl\\.[A-Za-z]+Format\\(\\)'`. `report-with-fix`; on an SSR route hand the hydration half to `ssr-safety.md`.
6. **`Intl.DateTimeFormat` with a locale but no `timeZone`.** Grep: `rg -n 'Intl\\.DateTimeFormat\\(' -A2` and check the options object. `report-with-fix` on SSR routes; on a CSR-only app it is `dismiss` with the reason (one runtime, one zone).
7. **Currency derived from locale.** BAD: `locale === 'de-DE' ? 'EUR' : 'USD'`. GOOD: currency read from the transaction / product / tenant. Grep: `rg -n "currency" -B2` near a locale comparison. `report-with-fix`.
8. **Namespace rendered before it loads.** A lazily-registered namespace whose consuming subtree has no awaited boundary. Grep: `rg -n 'setLocaleMessage|loadNamespaces|import\\(.*locales'` then check for an await/Suspense between the load and the first render of its consumers. `report-flagged` — the boundary placement is a route-shape decision.

## Closure verbs

Exactly one verb per finding. This pattern emits `report-with-fix`, `report-flagged` (namespace-loading boundaries, a key-architecture change that touches a shipped contract), `dismiss` (single-runtime formatting, a hosted platform that owns key naming), `halt-handoff` (locale count and RTL → `.claude/rules/i18n.md`; parity / unused / hardcoded → `@i18n-auditor` and `/i18n-audit`; hydration mismatch → `ssr-safety.md`), and `halt-missing-cite`.
