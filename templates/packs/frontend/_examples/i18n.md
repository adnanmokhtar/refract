# Pattern: i18n

> **Hard rule:** Every user-facing string is a translation key — no hardcoded literals in components. Locale parity (every key present in every locale) is CI-enforced, not eyeballed. Concatenating translated fragments, embedding HTML in keys, or skipping RTL/pluralization for "later" is forbidden.

**Halt conditions / mandatory cites**
- A new string MUST cite the translation key file at `<path:line>` for every locale (parity check).
- Date/number/currency formatting MUST cite the locale-aware formatter helper, not raw `toString`.
- A diff that hardcodes English in a component is a bug — reject.
- Hand-wave grep on `etc.`, `...`, `appears to`, `roughly` is forbidden when claiming "all strings are extracted".
- If the project's i18n library + locale layout isn't extracted, halt before adding strings.

Every user-facing string is a translation key. Locale parity is enforced in CI, not eyeballed during review. Treating i18n as a "we'll add it later" task means rewriting every component the day Arabic ships and discovering that "string concatenation works fine in English" is half a redesign in RTL.

## Context

Reach for first-class i18n when:
- The product ships in two or more languages, OR will within 12 months.
- Users span timezones / currencies / number-formatting locales (e.g., `1,000.00` in en-US vs `1.000,00` in de-DE vs `١٬٠٠٠٫٠٠` in ar-EG).
- You're in a regulated market that mandates the local language for legal text.

For an internal tool used by 10 engineers in one country, hardcoded English is fine and i18n adds noise. Don't pay the cost without the use case.

## Key structure

Namespace by feature, not by page. A "products" namespace is reused across list/detail/edit; a "page-1" namespace is unmaintainable when pages get renamed.

```yaml
# locales/en/products.yaml
list:
  title: "Products"
  empty: "No products yet — add your first one"
  search_placeholder: "Search products..."

form:
  name_label: "Name"
  name_placeholder: "Enter product name"
  price_label: "Price ({currency})"
  submit_create: "Create product"
  submit_update: "Save changes"

errors:
  duplicate_name: "A product with this name already exists"
  price_must_be_positive: "Price must be greater than zero"

count:
  zero: "No products"
  one: "{count} product"
  other: "{count} products"
```

The dot-path `products.form.price_label` is the ONLY identifier components reference. Reorganizing files inside the locale directory is safe; renaming a key is a contract change.

## Locale parity in CI

```bash
# .github/workflows/i18n-parity.yml (sketch)
- run: node scripts/check-i18n-parity.js
```

```js
// scripts/check-i18n-parity.js
import { readFileSync } from 'fs';
import { glob } from 'glob';
import { flatten } from 'flat';

const locales = ['en', 'ar'];
const trees = Object.fromEntries(
  locales.map(loc => [loc, mergeYaml(`locales/${loc}/*.yaml`)])
);
const keys = Object.fromEntries(
  locales.map(loc => [loc, new Set(Object.keys(flatten(trees[loc])))])
);

const missing = {};
for (const loc of locales) {
  const others = locales.filter(l => l !== loc);
  for (const other of others) {
    const diff = [...keys[other]].filter(k => !keys[loc].has(k));
    if (diff.length) (missing[loc] ||= []).push(...diff);
  }
}
if (Object.keys(missing).length) {
  console.error('Locale parity broken:', missing);
  process.exit(1);
}
```

Run on every PR. A missing key in any locale fails the build. This is the single most effective i18n investment — the alternative is "user reports text disappears in Arabic" tickets in week six.

## Plurals via ICU MessageFormat (not string concatenation)

```ts
// WRONG — breaks in any language with non-trivial plural rules (Arabic has 6 forms)
const text = `${count} ${count === 1 ? 'order' : 'orders'}`;

// RIGHT — ICU plural in the locale file, locale handles its own rules
// en.json: "{count, plural, =0 {No orders} one {# order} other {# orders}}"
// ar.json: "{count, plural, =0 {لا توجد طلبات} one {طلب واحد} two {طلبان} few {# طلبات} many {# طلبًا} other {# طلب}}"
const text = t('orders.count', { count: 5 });
```

Arabic distinguishes singular, dual, few (3-10), many (11-99), other. Russian has different forms for 1, 2-4, 5+. English only has one + other. ICU handles all of them; ternary operators handle none.

## Date / number / currency formatting

```ts
// WRONG — locks to one locale's conventions
const formatted = `$${price.toFixed(2)}`;
const date = new Date().toLocaleDateString();  // uses runtime locale, varies

// RIGHT — explicit formatter via Intl
const price = new Intl.NumberFormat(locale, { style: 'currency', currency: 'USD' }).format(4250);
//   en-US → "$4,250.00"   ar-EG → "٤٬٢٥٠٫٠٠ US$"   de-DE → "4.250,00 $"

const date = new Intl.DateTimeFormat(locale, { dateStyle: 'medium' }).format(new Date());
//   en-US → "Apr 24, 2026"  ar-EG → "٢٤ أبريل ٢٠٢٦"

// Better: wrap in i18n composable
const { d, n } = useI18n();
{{ n(price, 'currency', 'USD') }}
{{ d(date, 'medium') }}
```

Currency code is a separate concern from locale. A US user buying from a German store sees German prices in EUR; both `locale` and `currency` are needed for the format call.

## RTL coordination

When the active locale is RTL (Arabic, Hebrew, Persian, Urdu):

```html
<html :lang="locale" :dir="dir">
```

```ts
// composables/useDirection.ts
const RTL_LOCALES = new Set(['ar', 'he', 'fa', 'ur']);
export const useDirection = () => {
  const { locale } = useI18n();
  return computed(() => (RTL_LOCALES.has(locale.value) ? 'rtl' : 'ltr'));
};
```

CSS uses logical properties (`margin-inline-start` not `margin-left`) — see `rtl.md` for the full pattern. Setting `dir="rtl"` flips the layout but only if your CSS is logical-property-based.

## Cross-frontend key consistency

If you operate multiple frontends in one workspace (admin + storefront + mobile), use the SAME key for the same concept. Translators write "Order Total" once and both apps inherit it. Diverging keys (`orders.list.total` in admin, `cart.summary.total` in storefront) double the translation cost and create localization drift.

## Loading + lazy-loading namespaces

```ts
// Don't ship every locale to every user — lazy-load
i18n.global.setLocaleMessage('ar', await import(`./locales/ar.json`));
```

Per-namespace splitting helps further: a user on `/products` doesn't need the `/admin/users` namespace. Most i18n libraries (vue-i18n, react-i18next, next-intl) support per-namespace lazy loading.

## Trade-offs

Pro: keys decouple text from code; one designer change updates all language variants in one PR. Pro: parity CI catches missing translations before they reach users. Con: every string change requires touching N files (one per locale). Con: pluralization syntax is a new mini-language to learn. Con: "lorem ipsum" placeholders in dev mean you discover bad UX only after translation.

Don't over-i18n internal admin tooling read by 5 people who all speak the same language — the maintenance cost has no payback.

## Common mistakes

- **String concatenation to build sentences.** `"Welcome, " + name + ", to " + product` works in English, breaks word order in Japanese, and breaks direction in Arabic. Use `t('welcome.message', { name, product })` with `"Welcome, {name}, to {product}"` in the locale file — locale-appropriate word order is the translator's job.
- **Inline strings in templates "just for now".** They never get extracted later. Add `<template>{{ t('feature.string') }}</template>` from the start, even if the locale file is mostly English with placeholder Arabic.
- **Hardcoded `dir="ltr"` on the page.** Locks the entire app LTR regardless of locale. The `dir` attribute MUST be driven by the active locale.
- **Concatenated translations to dodge plurals.** `t('order') + ' x ' + count` produces "Order x 5" in English and gibberish elsewhere. Use ICU plural form.
- **Machine-translated copy committed without review.** Google Translate ships syntactically valid Arabic that uses the wrong dialect, wrong formality, or means something embarrassing. Every locale needs a human reviewer before launch.
- **Trusting `navigator.language` for the locale.** Browser language preference may differ from app preference. Persist the user's chosen locale per-user; use `navigator.language` only as a first-visit default.

## Testing

- Visual regression in EVERY declared locale for critical pages (login, checkout, settings). Component looks fine in English, breaks at "اشتراك مدفوع شهرياً" because the button is too narrow.
- Snapshot tests for translated strings: `expect(t('orders.count', { count: 5 })).toBe('5 orders')` per locale.
- E2E smoke test that switches locale and verifies a known string changes (catches "the locale switcher silently broke" regression).
- Locale parity check in CI as the merge blocker.

## Migration path

Retrofitting a hardcoded-English app:
1. Add the i18n library + a single locale (`en`) with one namespace per feature.
2. Inventory user-facing strings. The repo's own extractor produces the list — `i18next-parser`, `vue-i18n-extract`, or the `nuxt/i18n` extractor (whichever matches the installed i18n lib); the in-pack `/i18n-audit` command reports the gap when no extractor is wired. A manual sweep is the fallback, not the plan.
3. Replace strings file-by-file. PR per feature, not all at once — review burden is unbearable in one giant PR.
4. Add a second locale (Arabic, the highest-effort one) only after `en` is fully extracted. The mismatches surface RTL + pluralization issues immediately.
5. Wire parity CI. From now on every new key requires both locale entries.

## References

- ICU MessageFormat documentation (unicode.org/reports/tr35) — plural and select syntax reference.
- Mozilla Fluent (projectfluent.org) — alternative to ICU, more expressive for complex grammar; consider if ICU plurals feel limiting.
- vue-i18n / react-i18next / next-intl docs — pick one and follow its idioms; mixing strategies is the most common architectural drift.
