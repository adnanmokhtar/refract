# /verify-plan

## The Premise (read this first)

**Plan-fulfilled is mechanical. Refuse PASS unless every plan item has a citation.** A plan item with a `[ ]` checkbox doesn't count toward fulfillment until it's flipped to `[x]` AND backed by a `<file:line>` citation showing the actual code, OR a passing test name. "Looks done" without a cite = `⚠ deviated`. No partial credit.

**Mechanical halt** — refuse a PASS verdict if:
- ANY plan item is `⚠ deviated` or `✗ missing` (PASS requires 100% `✓ matched`).
- ANY checked item lacks a `<file:line>` or test-name citation.
- The implementation introduces files / behavior NOT mentioned in the plan (scope creep — flag explicitly).

Verify that an implementation (done by Claude Code, OpenCode, Cursor, Aider, or any other tool — or a human) matches the plan written by an earlier `--plan` run. The plan file is the contract; this command audits adherence.

## Usage

```
/verify-plan <plan-file-path>
/verify-plan .claude/plans/add-feature-prescription-filter-20260427-1430.md
/verify-plan --latest                            # picks newest plan in .claude/plans/
/verify-plan --plan-id phc-7f4a                  # locate by Plan ID embedded in any plan file
```

## Phase 1 — Understand (parse the plan)

- Resolve plan file path (explicit / `--latest` / `--plan-id` lookup).
- Validate plan file structure: must contain headers `## Context`, `## Inputs`, `## Outputs`, `## Steps`, `## Constraints`, `## Verification`, `## Status`. Missing headers = malformed plan = halt. `## Known unknowns` is an accepted OPTIONAL section — a plan with it must not fail; a plan without it must not fail.
- Extract:
  - Plan ID (`Plan ID: <hash>` from frontmatter — used in cross-references).
  - Generated timestamp (compare against current time for staleness check).
  - Project + stack (sanity-check against current `.claude/codebase-profile.md`).
  - Outputs list (CREATE / MODIFY / DELETE entries with paths).
  - Constraints list (DON'T-style rules).
  - Verification commands (lint / typecheck / test / curl).

## Phase 2 — Organize

Build the audit checklist:

- **Output checks** — one per CREATE/MODIFY/DELETE entry.
- **Constraint checks** — one per DON'T rule, grep / file-check based.
- **Verification checks** — execute each verification command.
- **Staleness check** — compare plan timestamp to git activity on touched paths.

## Phase 3 — Retrieve

For each Output entry, read the actual file (if exists) + git history since plan timestamp.

For each Constraint, identify the grep / file-check pattern that detects violation:
- "DON'T add a new dependency" → diff `requirements.txt` / `package.json` / equivalent against git state at plan timestamp.
- "DON'T modify queryset before tenant filter applies" → grep + line-order check on the named file.
- "DON'T change PrescriptionSerializer output shape" → diff the serializer file's serialized fields.
- "DON'T touch X" → confirm git history shows no changes to X since plan timestamp.

## Phase 4 — N/A (no generation in verify mode)

Verify is read-only. If drift is found, this command REPORTS — it does NOT auto-fix. The user decides whether to re-plan, re-implement, or accept drift.

## Phase 5 — N/A (no knowledge persistence beyond Status section)

The only write this command performs is updating the plan file's `## Status` section (checking boxes that pass; adding `## Verify run` log entry with timestamp + result summary).

## Phase 6 — Validate (the audit itself)

Run each check in order, accumulate results:

```
For each Output entry:
  Case CREATE <path> — <description>:
    File exists? ✓ / ✗
    File body matches description (heuristic — non-empty, addresses the entity)? ✓ / ⚠
    Git diff vs plan timestamp shows file added? ✓ / ⚠ (if file existed before, that's not CREATE)
  Case MODIFY <path> — <change>:
    File exists? ✓ / ✗
    Git diff vs plan timestamp shows change to file? ✓ / ⚠
    Change matches the described intent (heuristic — grep for expected keywords)? ✓ / ⚠
  Case DELETE <path>:
    File absent? ✓ / ⚠ (still exists)
    Git history shows deletion? ✓ / ⚠

For each Constraint:
  Run the constraint check (grep / file-check / diff).
  Pass = ✓; Fail = ✗ "constraint violated: <details>".

For each Verification command:
  Execute (Bash).
  Pass = ✓; Fail = ✗ with stderr surfaced.

Staleness:
  If git log shows touched files modified BEFORE plan timestamp by other commits → ⚠ "plan may be stale, files changed since plan written".
```

Output format:

```
VERIFY PLAN: <plan-id> — <one-line summary from plan header>
─────────────────────────────────────────────────────────────
Generated:   <plan timestamp>  (age: <Nh / Nd>)
Project:     <name>            ✓ matches current codebase-profile

Outputs (<expected> expected):
  ✓ CREATE <path> (<lines>) — <verification note>
  ✓ MODIFY <path> — <verification note>
  ⚠ MODIFY <path> — file changed but doesn't match description: <details>
  ✗ CREATE <path> — file does not exist

Constraints (<N>):
  ✓ <constraint>
  ✗ <constraint> — VIOLATION: <details>

Verification commands:
  ✓ <cmd>
  ✗ <cmd> — exit <code>: <stderr summary>

Staleness:
  ⚠ <path> modified by 2 commits AFTER plan written (commits: a1b2c3, d4e5f6) — plan may be stale

Drift summary:
  Outputs:        <X passed> / <Y total>
  Constraints:    <X passed> / <Y total>
  Verification:   <X passed> / <Y total>
  Staleness flags: <count>

Verdict: PLAN FULFILLED | PLAN DRIFTED | PLAN VIOLATED
```

**Verdict logic**:
- **PLAN FULFILLED** — all outputs ✓, all constraints ✓, all verification ✓, no staleness flags. Update plan Status section: all boxes checked, append `## Verify run` log entry with PASS.
- **PLAN DRIFTED** — outputs partial OR staleness flags raised. Doesn't violate constraints. User decision: accept (re-plan to capture reality) or re-implement (close the gaps).
- **PLAN VIOLATED** — at least one constraint failed OR verification failed. Halt + surface specifics. The implementation broke a hard rule the plan committed to.

## Phase 7 — Improve (feed the learning loop)

- If PLAN FULFILLED + no surprises: archive plan to `.claude/plans/_archive/` (optional; offer y/n).
- If PLAN DRIFTED: append a `## Drift notes` section to the plan documenting what diverged + why; queue an entry to `ai/dynamic/feedback-learned.md` so future plans are tighter on the drift category.
- If PLAN VIOLATED: append the violation to `ai/failures/_index.md` (or queue to `ai/dynamic/decisions-pending.md` if not yet a validated failure). The next agent that uses similar inputs sees the warning.

## Failure modes

- **Plan file malformed**: missing headers, no Plan ID, no timestamp → halt with "plan format invalid; regenerate via `<command> --plan`."
- **Plan file from different project**: project name in plan header doesn't match current `.claude/codebase-profile.md` → halt, suggest the user is in the wrong working directory.
- **Verification command requires interactive input** (e.g., needs DB password) → flag as ⚠, ask user to run manually + report result.
- **Constraint check ambiguous** (the constraint's pattern is genuinely hard to mechanically verify — e.g., "don't break UX") → flag as ⚠ "manual review required" with a one-liner pointer to what to check.

## Examples

```
$ /verify-plan .claude/plans/add-feature-prescription-filter-20260427-1430.md

VERIFY PLAN: phc-7f4a — Add status filter to prescriptions list
[...]
Verdict: PLAN FULFILLED  → archive plan to _archive/? [y/n]

$ /verify-plan --latest
[...]
Verdict: PLAN DRIFTED — 2 outputs missing
  Run /execute-plan <plan-file> to close the gaps from the plan, OR run /add-feature --plan to re-plan against current state.

$ /verify-plan --plan-id phc-7f4a
[...]
Verdict: PLAN VIOLATED — constraint "DON'T add a new dependency" failed (django-filter-extra added to requirements.txt)
  Halt. The implementation must remove the violation OR an ADR must be written justifying the override.
```
